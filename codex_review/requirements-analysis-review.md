# `requirements-analysis.md` 需求设计评审

## 评审范围

本评审对照以下材料完成：

- `.claude/skills/pdc-project1-development-process/SKILL.md`
- `.claude/skills/pdc-project1-architecture-standards/SKILL.md`
- `Projects1and2.pdf` 中 Project 1 的 Component 1.1–1.4、评分标准及提交要求
- `docs/requirements/requirements-analysis.md`

## 总体结论

文档结构完整，已经覆盖角色、功能需求、业务规则、数据模型、CUI 交互、范围、约束、非功能需求和验收场景，且“智能”被限定为可解释的成绩规则计算，方向符合 Project 1。

当前版本仍不适合作为最终需求基线。主要风险是功能范围过大、交互命令与业务值冲突、学生转班后的成绩归属无法由数据模型表达，以及部分状态和持久化规则无法被稳定实现或验收。

## 必须优先修正的问题

### 1. Project 1 范围偏大

**等级：严重**

第 3.1 节将 11 个模块全部标为 `Must`，同时要求完整 CRUD、权限控制、密码安全、CSV 损坏行处理、原子写入、统计排名、规则预警、跨平台验证等功能。

这与开发规范 H1“规模适中”和 PDF 评分标准中“既不简单也不过度复杂”的要求存在风险。两人项目很容易出现功能做不完、设计与代码不一致、CUI 流程不稳定等问题。

**建议：** 明确 Essential / Optional / Rejected；保留能够形成“班级—学生—课程—成绩—统计/预警”闭环的功能，其余模块降级或删除，并为取舍写出学生本人作出的理由。

### 2. `0` 返回命令与合法成绩 0 冲突

**等级：严重**

- FR-SCORE 允许成绩范围为 `[0, 100]`。
- 第 6.4 节规定任意界面输入 `0` 返回。
- 第 6.5 节成绩录入示例写着“0 返回”。
- AC-18 要求任意界面输入 `0` 返回。

按当前规则，成绩 0 无法录入，需求之间不可同时满足。

**建议：** 仅在菜单选择、对象选择等命令提示中把 `0` 解释为返回；在成绩、容量、日期和文本字段中使用单独的取消命令或明确的 `cancel` 语法。

### 3. 学生转班会破坏历史成绩归属

**等级：严重**

FR-STU-05 要求学生转班时保留已有成绩，并要求新班级开齐这些成绩对应的课程。但 `Score` 只有 `studentId` 和 `courseId`，没有 `classId` 或 `classCourseId`。

如果班级通过 `Student.classId` 推导，学生转班后旧成绩会被统计到新班级，原班级历史统计也会改变。当前数据模型无法同时支持“保留历史成绩”和“按班级统计历史结果”。

**建议：** 优先让 Score 保存不可变的班级/教学任务引用；或者明确禁止已有成绩的学生转班；如果成绩确实随学生迁移，也必须明确所有统计的迁移语义。

### 4. 班级状态没有生命周期规则

**等级：严重**

文档定义了 `PLANNED / ACTIVE / FINISHED`，并规定 FINISHED 班级不能新增学生、转班或新增教学任务，但没有说明：

- 谁可以修改状态；
- 允许哪些状态转换；
- 是否由开始/结束日期自动决定；
- 已结束日期与手工状态冲突时以什么为准。

因此 FINISHED 相关限制无法稳定实现和测试。

**建议：** 增加状态转换表、修改入口、权限和非法转换的验收场景。

### 5. 教学任务是否允许暂时没有任课教师不明确

**等级：严重**

FR-TEACH-02 允许先向班级添加课程，FR-TEACH-03 再分配教师；但数据关系把 Employee 与 ClassCourse 表达为 `1..*`，FR-SCORE 又拒绝“无任课教师”的成绩录入。

当前无法判断 `teacherId` 是否可以为空，也无法判断未分配教师的任务如何展示、修改和删除。

**建议：** 明确 `teacherId` 的可空性和任务生命周期；如果允许未分配状态，应在模型、关系多重性、CUI 提示和验收标准中统一表达。

### 6. 多文件持久化的“原子写入”不足以保证业务一致性

**等级：严重**

FR-SYS-05 要求原子写入，但一个业务操作可能同时修改多个文件：

- 删除学生并级联删除成绩；
- 删除班级并级联删除教学任务；
- 转班并更新学生及相关关系。

即使每个 CSV 单独使用临时文件替换，程序在两个文件之间中断时仍可能留下部分提交状态。

**建议：** 明确操作级事务、全量快照、回滚或一致性恢复策略；否则应把要求改成“单文件安全替换”，不要表述为完整业务原子性。

## 需求完整性和可验证性问题

### 7. 多项 CRUD 需求没有定义完整修改范围

**等级：中等**

功能总览写的是 CRUD，但具体需求不完整：

- FR-CLASS-03 只说明容量修改，没有说明班级名称、日期、状态等字段；
- FR-COURSE-03 只说明课程编号唯一，没有说明名称和说明是否可改；
- FR-STU-04 没有列出可修改字段和转班边界；
- FR-EMP-04 没有说明角色、状态、联系方式等字段的修改规则。

**建议：** 为每个修改操作列出可变字段、必填字段、唯一性约束、引用影响和验收结果。

### 8. 验收标准没有覆盖所有 Must 需求

**等级：中等**

AC-01 至 AC-20 覆盖了登录、若干删除约束、成绩、权限、持久化和预警，但没有覆盖部门新增/修改、员工筛选与重置密码、课程 CRUD、班级状态修改、教学任务增删改等多个核心功能。

**建议：** 增加 FR → AC 追溯表，确保每条 Must 需求至少对应一个可执行验收场景。

### 9. CSV 损坏行的引用完整性处理不明确

**等级：中等**

FR-SYS-06 要求跳过无法解析的行并提示行号，但没有说明坏行造成以下情况时如何处理：

- 外键引用不存在；
- ID 重复；
- 学生存在但班级不存在；
- 成绩存在但学生或课程不存在。

**建议：** 定义加载顺序、校验阶段、错误分类、跳过/拒绝策略和最终诊断汇总，避免“能启动但数据已部分丢失”。

### 10. 性别字段没有输入和业务规则

**等级：中等**

Employee 和 Student 数据模型包含 `gender`，列表也要求展示性别，但第 4.4 节没有说明是否必填、允许值、空值表示和修改规则。

**建议：** 增加枚举或明确自由文本规则，并同步更新 CSV 格式、初始化数据和验收场景。

### 11. 密码哈希要求缺少实现参数

**等级：中等**

文档只规定“加盐哈希”，没有指定算法、迭代参数、盐长度、编码方式或验证失败处理。不同实现可能都声称满足要求，但安全性和可复核性差异很大。

**建议：** 在约束中固定一种 JDK 可用方案及参数，并说明密码升级或旧格式处理策略（如确实需要）。

### 12. 禁用仍有教学任务的教师会留下失效任务

**等级：中等**

文档允许禁用仍有教学任务的教师，但禁用后该教师不能登录，原任务仍保留，只有管理员可以继续处理成绩。没有自动改派、待改派状态或清理流程。

**建议：** 要么禁用前必须完成改派，要么增加明确的“待改派”状态和管理员处理流程，并补充统计、预警和成绩权限规则。

### 13. 全局 `Q` 退出规则会与数据输入冲突

**等级：中等**

第 6.4 节规定“Q 任意输入处安全退出”。这会使姓名、课程名称或说明字段中的合法 `Q` 值无法输入，也没有大小写和转义规则。

**建议：** 将 `Q` 限定为菜单/命令提示，普通数据字段不解释全局退出命令。

## 角色、文档交付和设计追溯问题

### 14. 利益相关者与系统 actor 混用

**等级：中等**

第 2 节列出“课程评审者”和“项目开发者”。他们可以是利益相关者，但不是系统操作 actor。架构规范要求用例图中的 actor 使用实际系统角色。

**建议：** 用例图主要保留 ADMIN、TEACHER；把评审者和开发者放到利益相关者或项目背景说明中。

### 15. 学生自撰 Critical Reflection 尚未交付

**等级：提交风险**

文档明确说明不包含学生自撰 Critical Reflection。作为拆分的需求文档可以接受，但 PDF 的 Component 1.1 明确要求学生说明：哪些功能必要、哪些不必要或不现实，以及取舍原因。

最终报告必须另附学生本人撰写的反思；本文件中的功能表和“待评审项”不能替代该反思。

### 16. 需求文档不能替代 Project 1 的设计工件

第 5 节的数据模型可以作为类图输入，但不能替代架构规范要求的：

- 用例图；
- 第一轮类图；
- GenAI 批判分析与采纳/拒绝记录；
- 第二轮最终类图；
- 两轮演进说明；
- 学生自撰设计反思。

最终类图还必须与实际 Java 类、方法、关系和分层结构一致。

## 建议的修订顺序

1. 先确定 Essential 功能并削减范围。
2. 修复 `0`/`Q` 命令语义。
3. 修正 Score 与学生转班的历史归属模型。
4. 补充班级状态和 ClassCourse 生命周期。
5. 定义跨文件持久化的一致性和损坏数据处理策略。
6. 为所有 CRUD 补全字段级规则，并建立 FR → AC 追溯表。
7. 另行完成学生自撰需求反思、两轮设计工件和 AI Usage Log。
