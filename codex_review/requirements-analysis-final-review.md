# `requirements-analysis.md` 最终复审报告

## 复审范围与结论

本次只复审 `docs/requirements/requirements-analysis.md` 的需求内容，并对照 Project 1 规范和评分要求。按用户要求，本次**不检查学生自撰反思、用例图、两轮类图、演进说明或 AI Usage Log 的文件是否存在及其质量**。

结论：v0.2 已实质修正上一轮大部分关键问题，包括成绩绑定不可变 `classCourseId`、命令输入范围、班级状态转换、待分配教学任务、字段级修改规则、密码哈希参数和 FR→AC 追溯。整体已接近可作为需求基线，但仍有几处需求矛盾或初始化边界不清，建议修完再冻结版本。

## 仍需修正的问题

### 1. Must 与“增强项”优先级互相矛盾

**严重程度：高**

第 3.1 节把 FR 模块及其所有条目定义为 Must；随后把批量录入、特定筛选和重置密码标为增强项，但又写明它们仍是 Must，且必须通过验收。这样“增强项”并没有降低范围，只是改变实现顺序，无法回应项目规模风险。

**建议：** 将具体增强需求的优先级改为 Should（或明确为 Must 的分阶段实现且验收时间不同）。若它们确属交付必需，则删除“增强项”表述，并重新论证整体规模适合团队完成。

### 2. 学生预警等级的判定流程自相矛盾

**严重程度：高**

3.11.1 写“按优先级从高到低判定，命中即停止”，后文又要求“若多个条件同时命中，展示全部命中规则，等级取最高”。若命中即停止，就无法收集后续命中规则；若展示全部，则必须评估全部条件。

**建议：** 改成“评估全部适用条件，收集全部命中规则，最终等级取最高优先级”；单独说明“数据不足”不参与等级计算。

### 3. 初始化演示数据可能违反班级状态规则

**严重程度：高**

FR-CLASS-02 规定新建班级初始状态为 PLANNED；FR-STAT/FR-SCORE 的规则又规定 PLANNED 班级不能录入成绩（4.3）。但 5.4 要求首次运行生成已有成绩的演示数据，却没有为演示班级指定 ACTIVE/FINISHED 状态。按默认创建规则，这组种子数据可能在启动时就违反业务约束。

**建议：** 明确种子班级状态为 ACTIVE（并配置合理日期），或明确初始化数据通过受控导入建立且之后仍需满足同一状态约束。对应增加验收检查。

### 4. 不完整数据文件的初始化及默认管理员依赖关系不清

**严重程度：高**

FR-SYS-01 要求缺失文件时创建空文件，FR-SYS-02 又规定“首次运行”才写入默认管理员和演示数据，另在缺少可用管理员时创建默认管理员。没有说明已有部分数据、缺少单个核心文件、缺少部门文件但管理员文件存在等情况下如何补齐关联数据。新建默认管理员还需要其部门存在，否则可能违反外键规则。

**建议：** 定义初始化场景矩阵：全新目录、部分文件缺失、文件为空、管理员缺失、依赖部门缺失。逐种规定是否只补账号、是否补演示数据、怎样避免覆盖已有数据，以及默认管理员部门如何保证存在。

### 5. Student 的转班状态条件仍然含糊

**严重程度：中**

FR-STU-05 说目标班级“未结束”，状态表则将 FINISHED 作为结束状态，并另有开始/结束日期。当前未明确 PLANNED 班级是否可接收转入学生，也未明确日期已过但状态仍为 PLANNED 时是否仍可转入。文档虽规定状态不随日期自动变化，但“未结束”仍可被理解为状态或日期条件。

**建议：** 直接写成目标班级状态必须是 PLANNED 或 ACTIVE，并注明日期只展示、不影响可转入判断（或明确采用的日期规则）。同时写清转班是否需要学籍状态为 ACTIVE。

### 6. 员工状态字段存在通用修改与专用流程重叠

**严重程度：中**

FR-EMP-04 和 4.6 将 Employee.status 列为普通可变字段，但 FR-EMP-06 对启用/禁用规定了最后一个管理员、教学任务引用和登录影响等专门规则。若一般“修改员工资料”也能修改 status，可能绕过启停流程。

**建议：** 从 FR-EMP-04 和一般修改字段中移除 status；只允许通过 FR-EMP-06 的专用状态转换操作修改，并在 4.6 注明。

### 7. 学生预警“无成绩”的范围需要按角色限定

**严重程度：中**

FR-WARN-05 写学生“无任何成绩”显示数据不足；FR-WARN-04 又规定教师只能基于本人任课 ClassCourse 的成绩计算。一个学生可能有其它教师课程的历史成绩，但在当前教师的范围内没有成绩，此时两条规则给出的结果不明确。

**建议：** 明确“数据不足”按当前请求者可见范围判断：管理员看全体成绩，教师只看本人任课 ClassCourse；并为教师在可见范围无成绩的学生增加验收场景。

### 8. 多项业务边界尚未有直接验收场景

**严重程度：中**

FR→AC 表已经补齐模块级覆盖，但部分关键规则没有独立 AC，例如：PLANNED 班级禁止录成绩、教师预警的范围、最后一个启用管理员保护、员工状态不能通过普通资料修改绕过、部分数据文件缺失时的启动行为。

**建议：** 在修订上述规则后为每条增加对应场景；避免只用一个宽泛 AC 覆盖多个条件分支。

## 建议处理顺序

1. 统一 Must / Should / 增强项的优先级含义。
2. 修正预警规则“命中即停止”与“列出全部触发项”的冲突。
3. 固定种子班级状态并保证演示成绩符合状态规则。
4. 补全缺失文件与默认管理员的初始化矩阵。
5. 明确转班目标状态、员工状态修改入口和教师预警数据范围。
6. 为新增的边界规则补充验收场景。
